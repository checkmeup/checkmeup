- [EP-10](../stories/ep-10-theme.md) Light & dark theme — Jun 17. The public status page (separate Go-rendered template, already fixed-light) was descoped — see the epic file. Surfaced and fixed two real pre-existing bugs along the way: (1) `bg-[--token]`/`text-[--token]` Tailwind arbitrary-value classes were compiling to invalid CSS (missing `var()`) across `Button.vue`, `Input.vue`, `Label.vue`, and `LandingLayout.vue` — silently broken since whenever those components were built, just unnoticed because it happened to look passable in dark mode (e.g. the sign-in button had no visible background in *either* theme, just white text); (2) the `HomeView`/`PricingView`/`AboutView` CTA banner gradient blended into `var(--surface)`, which flips white in light mode, with theme-dependent text on top — fixed with dedicated `--cta-*` tokens so the banner stays an intentional green wash in light mode and a dark gradient in dark mode, instead of either an invisible button or a washed-out box.
- [EP-23](../stories/ep-23-suggest-a-feature.md) Suggest a feature — Jun 18, full epic (3/3). Rate-limited 5/hour per IP and 20/hour per org with a clear JSON error instead of httprate's plain-text default. Docs page "Need help?" section links to it; Settings nav already covers the signed-in entry point since the form lives on that page.

Linked from the footer (landing + public status pages), and sign-up links to the "Getting started" category.
- [EP-27](../stories/ep-27-annual-billing.md) Annual billing — Jun 18, full epic (3/3). Migration 014 added `orgs.billing_cycle`; the LemonSqueezy webhook and checkout-creation flow are cycle-aware (3 new `LS_*_ANNUAL_VARIANT_ID` env vars), verified end-to-end against the live DB with a simulated signed webhook (subscribe → annual Solo, then cancel → correctly reverts to Hobby/monthly). Pricing page has a monthly/annual toggle (Solo $90/yr, Startup $290/yr, Enterprise $990/yr — each exactly 10× monthly, "2 months free").

Built the real Billing-page upgrade UI (was "coming soon" since MVP launch): checkout buttons + the EP-27 monthly/annual toggle, redirecting to LemonSqueezy. Added an inline upgrade prompt (`UpgradePrompt.vue`) wired into all 4 create flows (cron/uptime/SSL monitors, status pages) via a new `ApiError.code` field, so a `402 plan_limit_reached` shows a real CTA instead of a generic error. - [EP-13](../stories/ep-13-email-alerts.md) Email alerts — Jun 18, full epic (5/5). Second alert channel alongside Telegram, reusing the existing Resend integration ([ADR-012](../decisions/012-email-resend.md), updated — alerts are no longer Telegram-only). Migration 015 added `orgs.alert_email` (defaults to the account owner's email at signup) and `orgs.email_alerts_enabled` (org-level toggle, off by default, independent of the Telegram connection). Down/recovery alerts dispatch to every enabled channel independently — a failure on one channel doesn't block the other — and the per-incident `max_alerts_per_incident` cap ([ADR-016](../decisions/016-alert-debounce.md)) now counts one notification event per alert regardless of how many channels it went out on, instead of per-channel.
- [EP-11](../stories/ep-11-keyword-monitoring.md) Keyword monitoring — Jun 18, full epic (5/5). Extends the uptime monitor's existing HTTP check ([EP-03](../stories/ep-03-uptime-monitor.md)) with an optional substring search on the response body — catches a maintenance page served with `200`, an error embedded in a JSON payload, or other content-level failures a status code alone misses. Migration 016 added a `keyword_mode` enum (`contains`/`not_contains`) plus `orgs.uptime_monitors.keyword`/`keyword_case_sensitive`, and `uptime_checks.failure_reason` (nullable text, e.g. "Keyword not found" vs "HTTP 500" — the raw response body itself is never stored). The check runs inside the existing single HTTP request, reading at most 512 KB of the body regardless of `Content-Length`, with a plain substring search (no regex, to avoid a ReDoS surface). Keyword failures reuse the exact same 2-consecutive-failure / alert-cap / recovery state machine as status-code failures, so enabling a keyword check doesn't introduce a second, parallel alerting path. Verified live against a local test server: contains-mode pass/fail, not-contains-mode, the down transition after 2 consecutive keyword failures, and recovery. Gated to paid plans same day ([ADR-019](../decisions/019-plan-limits.md) revised) — Hobby gets a `402 plan_limit_reached` on create/update when setting a keyword; `GET /api/v1/billing` exposes `keywordMonitoringEnabled` so the UI hides/disables the fields instead of round-tripping the error, and a keyword set before a downgrade survives but can only be cleared, not changed, until re-upgrading.
- Testing pass (v1.4) — Jun 19. ~190 test cases added across the Go backend (auth, billing, maintenance windows, cron and SSL monitors, the public ping endpoint, settings, status pages), run against a real Postgres instance rather than mocks. Found and fixed a real security issue along the way: status pages could attach a monitor without verifying it belonged to the org. Also fixed during the pass: sign-up no longer leaves an orphaned record behind on partial failure, the LemonSqueezy billing webhook rejects requests instead of accepting them unsigned if the webhook secret is misconfigured and no longer silently drops a failed plan update, and a cron monitor with alerts disabled now correctly clears its incident history on recovery.
- Cleanup (v1.5) — Jun 20. Fixed a plan-limit bug where editing an uptime monitor ignored the plan's minimum check interval (`Create` already enforced it correctly; `Update` floored to a fixed 10 minutes regardless of plan). Migrated all dashboard views to shared TanStack Query composables. Replaced remaining hardcoded hex colors with design tokens, including a new `--on-accent` token, fixing a dark-mode color bug. Added test coverage for billing plan limits and the config package.
- [EP-28](../stories/ep-28-notification-channels.md) Notification channels (v1.6) — Jun 21, 5/5 stories. Replaces the single org-level Telegram chat ID / alert email with a `notification_channels` table and per-monitor routing ([ADR-023](../decisions/023-notification-channels.md)). Migration 017 added `notification_channels` + `monitor_notification_channels`; the backfill migrated every org's existing Telegram/email settings into the new model with no observable change in dispatch behavior, and the `dispatchAlert` cutover shipped in the same release as the backfill, per the ADR-023 plan. A monitor with zero attached, enabled channels now falls back to emailing every user in the org instead of going silent. Legacy `orgs.telegram_chat_id`/`alert_email`/`email_alerts_enabled` columns are intentionally still in place pending a later drop migration. Also this release: the keyword monitoring plan gate added Jun 18 ([ADR-019](../decisions/019-plan-limits.md), revised) was removed again — keyword monitoring is free on every plan, including Hobby, since the gate had quietly become an always-true check. Plus: Docker image now runs as a non-root user, the SSL monitor's own TLS dialer enforces a TLS 1.2 floor, the notification channel picker warns when every selected channel is individually disabled, and the email-sending package and frontend bootstrap file got their first test coverage. Follow-up Jun 24: the channel picker was wired into the monitor *create* forms as well (previously only the edit view), so channels can be selected at creation time without a second edit step.
- [EP-14](../stories/ep-14-webhook-alerts.md) Webhook alerts (v1.7) — Jun 22, 5/5 stories. Third alert channel alongside Telegram and email, on top of EP-28's `notification_channels` model — a webhook channel's `config` JSONB holds `url` (must be `https://`) and a server-generated `secret`. Migration 018 added the `webhook` value to `notification_channel_type` and `last_delivery_status`/`last_delivery_detail`/`last_delivery_at` columns. New `internal/webhook` package mirrors `telegram.Client`'s shape: 10 s timeout, one attempt (no retries), every request signed with HMAC-SHA256 over the raw body in an `X-Checkmeup-Signature` header. The signing secret is intentionally returned unmasked in API responses (unlike the general guidance in ADR-023) since US-1403 requires it stay visible so users can configure verification on their end; it can only be rotated via a dedicated `POST /notification-channels/{id}/regenerate-secret`, never through a regular field update. Found and fixed a real gap while wiring this up: the cron monitor's recovery alert (`ping.go`) had never been cut over to the EP-28 channel model — it still read the legacy `orgs.telegram_chat_id`/`alert_email` fields directly, so recovery alerts silently ignored any `notification_channels` configuration. Refactored it to call the same `worker.DispatchAlert` the rest of the worker uses, which fixes that gap for Telegram/email too, not just webhook. Verified end-to-end against the live API and worker loop (not just unit tests): real HTTPS round-trip to a public endpoint via the test-webhook button, and a real signed down/recovery delivery from the worker loop with the HMAC independently recomputed and matched.
- [EP-29](../stories/ep-29-domain-expiry-monitoring.md) Domain expiry monitoring — Jun 23, 3/5 stories (US-2901, US-2904, US-2905 fully done; US-2902 and US-2903 each shipped with one AC deliberately not built). Sibling to the SSL monitor (EP-04): same table/worker/handler/alert-threshold shape, watching domain registration expiry instead of TLS certificate expiry. Migration 019 added `domain_monitors` (`domain_monitor_status` enum: waiting/up/expiring_soon/expired/error/paused), counted into ADR-019's aggregate monitor limit alongside cron/uptime/SSL. New `internal/rdap` package looks up registrar and expiry via RDAP (RFC 9082/9083) against the [rdap.org](https://rdap.org) bootstrap redirector, with an injectable `*http.Client`/base URL so both the success and failure paths are unit-testable against a local server — unlike the SSL monitor's `performTLSCheck`, which can only test its error path without a live network dependency. Reuses the SSL monitor's 30/14/7-day alert-threshold logic (`sslCrossedThreshold`) rather than duplicating it. Two ACs were intentionally dropped rather than half-built: a WHOIS text-parsing fallback for TLDs without RDAP support, and alerting immediately on a registry hold/pending-delete status (the RDAP client doesn't parse the domain `status` array yet). Full CRUD UI (list/create/detail/edit), dashboard card, sidebar nav, and wiring into the maintenance-window and status-page monitor pickers alongside cron/uptime/SSL.
- [EP-30](../stories/ep-30-status-badges.md) Public status badges — Jun 23, full epic (4/4). Embeddable per-page and per-monitor SVG badges (`GET /status/:slug/badge.svg`, `GET /status/:slug/badge/:monitor_id.svg`), hand-rendered server-side (no external badge service, no new dependency) with the same operational/degraded/outage wording as the page banner — `loadRows` was factored out of the existing HTML status-page handler so a badge can never disagree with what the banner shows, including maintenance-window overrides. Per-monitor badges 404 if the monitor isn't attached to that page, via a new `GetStatusPageMonitor` sqlc query scoped by `page_id` + `monitor_id`. `Cache-Control: max-age=60` plus a new IP-keyed 300/min rate limit on both routes — [ADR-013](../decisions/013-rate-limiting.md) updated, and its table backfilled with four other already-shipped routes (`/webhook/telegram`, `/webhook/lemonsqueezy`, `/suggestions`, `/notification-channels/{id}/test`) that had never been documented there. Status page detail view gets a new "Badges" card: live `<img>` preview per badge, one-click copy for both the Markdown (`![status](...)`) and HTML (`<a><img></a>`) embed forms.
- [EP-31](../stories/ep-31-assertion-checks.md) Assertion-based API checks (v1.9) — Jun 23, 4/5 stories (US-3101–US-3104; US-3105 multi-step chaining deliberately deferred per the story's own re-scoping note). Extends the uptime monitor's existing keyword check (EP-11) with two new structured conditions: JSON field assertions and a response-time threshold. Migration 020 added `json_assertions JSONB NOT NULL DEFAULT '[]'` and `max_response_time_ms INT` to `uptime_monitors`. Each check now evaluates assertions in a defined order — status code → keyword → JSON assertions → response-time threshold — and stops at the first failure, recording a distinct reason ("response is not valid JSON", "JSON assertion failed: …", "response time exceeded") rather than a generic one. JSON path resolution supports dot-notation (`data.status`, `$.status`) with comparators `equals`, `not_equals`, `contains`, `greater_than`, `less_than`; body is still capped at 512 KB, consistent with EP-11. Monitors with no assertions configured are entirely unaffected. Create/edit forms show an inline assertion builder (add/remove rows of path + comparator + expected value) and a max-response-time field; the detail view shows the configured assertions alongside the existing keyword line, and failure reasons in the check log already distinguish the new conditions.
- [EP-17](../stories/ep-17-slack-alerts.md) Slack alerts — Jun 24, 5/5 stories. Sixth alert channel built as a thin Slack-specific formatter on top of EP-14's generic webhook delivery — Slack Incoming Webhooks are a plain HTTPS POST, no OAuth app or approval process required. The only real difference from EP-14 is the payload shape: Block Kit blocks with monitor name, type, reason/duration, and timestamp instead of checkmeup's generic event JSON. URL validated against the `hooks.slack.com/...` pattern before save; "Send test message" verifies the connection before saving. Delivery failures (non-2xx from Slack, e.g. a removed webhook returning 404) are recorded in Settings as `last_delivery_status`/`last_delivery_detail`, consistent with the generic webhook channel. The per-incident alert cap ([ADR-016](../decisions/016-alert-debounce.md)) counts Slack triggers the same way as every other channel — one event across all attached channels combined, recovery always exempt.
