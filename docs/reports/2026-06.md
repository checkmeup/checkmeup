## Shipped

- MVP launch — Jun 16 (9 weeks ahead of the original Aug 14 target). Cron, uptime, and SSL monitors; Telegram alerts; status pages; billing. See [mvp-history.md](../mvp-history.md).
- [EP-09](../stories/ep-09-maintenance-windows.md) Maintenance windows — Jun 16, first post-MVP feature. The landing page and blog already promised this ahead of implementation. Migration 011 added `maintenance_windows` + `maintenance_window_monitors`; monitors under an active window are excluded from the worker's due/overdue queries, the same mechanism already used for `paused` (see [ADR-020](../decisions/020-maintenance-windows.md)).
- [EP-21](../stories/ep-21-terms-and-privacy.md) Terms and Privacy — Jun 17. Closed a real compliance gap (live product, no published legal docs). `/terms` and `/privacy` pages, required acceptance checkbox at sign-up, a blocking re-accept screen on version mismatch, and a read-only acceptance record in Settings. Migration 012 added `terms_version`/`terms_accepted_at` to `users`.
- [EP-10](../stories/ep-10-theme.md) Light & dark theme — Jun 17. Light palette added alongside the existing dark tokens, switched via `data-theme` on `<html>`, persisted in `localStorage`, defaults to OS `prefers-color-scheme` for first-time visitors, no flash on load. The public status page (separate Go-rendered template, already fixed-light) was descoped — see the epic file. Surfaced and fixed two real pre-existing bugs along the way: (1) `bg-[--token]`/`text-[--token]` Tailwind arbitrary-value classes were compiling to invalid CSS (missing `var()`) across `Button.vue`, `Input.vue`, `Label.vue`, and `LandingLayout.vue` — silently broken since whenever those components were built, just unnoticed because it happened to look passable in dark mode (e.g. the sign-in button had no visible background in *either* theme, just white text); (2) the `HomeView`/`PricingView`/`AboutView` CTA banner gradient blended into `var(--surface)`, which flips white in light mode, with theme-dependent text on top — fixed with dedicated `--cta-*` tokens so the banner stays an intentional green wash in light mode and a dark gradient in dark mode, instead of either an invisible button or a washed-out box.
- [EP-23](../stories/ep-23-suggest-a-feature.md) Suggest a feature — Jun 18, full epic (3/3). In-app form in Settings posts to `POST /api/v1/suggestions`, stores to a new `feature_suggestions` table (migration 013), and emails the founder via Resend — same direct-to-founder model as the existing `mailto:`/GitHub links (`DocsView.vue`), not a ticketing system. Rate-limited 5/hour per IP and 20/hour per org with a clear JSON error instead of httprate's plain-text default. Docs page "Need help?" section links to it; Settings nav already covers the signed-in entry point since the form lives on that page.
- [EP-22](../stories/ep-22-faq.md) FAQ — Jun 18, full epic (3/3). New `/faq` page with 5 categories (Getting started, Billing & plans, Monitors & alerts, Status pages, Privacy & security), backed by a shared `faq/faqs.ts` data module. `PricingView.vue`'s 6 billing entries moved there as the single source of truth — the pricing page now imports the `billing` category instead of keeping its own copy, with a "See all FAQs →" link. Linked from the footer (landing + public status pages), and sign-up links to the "Getting started" category.
- [EP-27](../stories/ep-27-annual-billing.md) Annual billing — Jun 18, full epic (3/3). Migration 014 added `orgs.billing_cycle`; the LemonSqueezy webhook and checkout-creation flow are cycle-aware (3 new `LS_*_ANNUAL_VARIANT_ID` env vars), verified end-to-end against the live DB with a simulated signed webhook (subscribe → annual Solo, then cancel → correctly reverts to Hobby/monthly). Pricing page has a monthly/annual toggle (Solo $90/yr, Startup $290/yr, Enterprise $990/yr — each exactly 10× monthly, "2 months free").
- [EP-07](../stories/ep-07-billing.md) Billing & plan limits — Jun 18, closed its last 2 deferred ACs (3/3, no caveats left). Built the real Billing-page upgrade UI (was "coming soon" since MVP launch): checkout buttons + the EP-27 monthly/annual toggle, redirecting to LemonSqueezy. Added an inline upgrade prompt (`UpgradePrompt.vue`) wired into all 4 create flows (cron/uptime/SSL monitors, status pages) via a new `ApiError.code` field, so a `402 plan_limit_reached` shows a real CTA instead of a generic error. Checkout requests now send an explicit `product_options.redirect_url` instead of relying on a LemonSqueezy dashboard default. Billing itself isn't *live* yet — the LemonSqueezy store, all 6 variants, API key, and webhook are configured, but the store is in LemonSqueezy Test mode pending their identity verification review (1-2 business days, in progress). See [`docs/billing-setup.md`](../billing-setup.md) for status and the remaining checklist.
- [EP-13](../stories/ep-13-email-alerts.md) Email alerts — Jun 18, full epic (5/5). Second alert channel alongside Telegram, reusing the existing Resend integration ([ADR-012](../decisions/012-email-resend.md), updated — alerts are no longer Telegram-only). Migration 015 added `orgs.alert_email` (defaults to the account owner's email at signup) and `orgs.email_alerts_enabled` (org-level toggle, off by default, independent of the Telegram connection). Down/recovery alerts dispatch to every enabled channel independently — a failure on one channel doesn't block the other — and the per-incident `max_alerts_per_incident` cap ([ADR-016](../decisions/016-alert-debounce.md)) now counts one notification event per alert regardless of how many channels it went out on, instead of per-channel.
- [EP-11](../stories/ep-11-keyword-monitoring.md) Keyword monitoring — Jun 18, full epic (5/5). Extends the uptime monitor's existing HTTP check ([EP-03](../stories/ep-03-uptime-monitor.md)) with an optional substring search on the response body — catches a maintenance page served with `200`, an error embedded in a JSON payload, or other content-level failures a status code alone misses. Migration 016 added a `keyword_mode` enum (`contains`/`not_contains`) plus `orgs.uptime_monitors.keyword`/`keyword_case_sensitive`, and `uptime_checks.failure_reason` (nullable text, e.g. "Keyword not found" vs "HTTP 500" — the raw response body itself is never stored). The check runs inside the existing single HTTP request, reading at most 512 KB of the body regardless of `Content-Length`, with a plain substring search (no regex, to avoid a ReDoS surface). Keyword failures reuse the exact same 2-consecutive-failure / alert-cap / recovery state machine as status-code failures, so enabling a keyword check doesn't introduce a second, parallel alerting path. Verified live against a local test server: contains-mode pass/fail, not-contains-mode, the down transition after 2 consecutive keyword failures, and recovery. Gated to paid plans same day ([ADR-019](../decisions/019-plan-limits.md) revised) — Hobby gets a `402 plan_limit_reached` on create/update when setting a keyword; `GET /api/v1/billing` exposes `keywordMonitoringEnabled` so the UI hides/disables the fields instead of round-tripping the error, and a keyword set before a downgrade survives but can only be cleared, not changed, until re-upgrading.
