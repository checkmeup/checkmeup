# ADR-021: Versioning via semantic-release, build stamping via git describe

**Status:** Accepted
**Date:** 2026-06-16

## Context

Commits were already enforced as Conventional Commits via commitlint (`.commitlintrc`, husky `commit-msg` hook), but there was no versioning: no git tags, no CHANGELOG, and nothing in the running app reported what was actually deployed. The repo ships a single Docker image (frontend + backend built together by `Dockerfile`, deployed manually via `kamal deploy`) — there's no case for independent per-package versions.

## Decision

**Release metadata** (semver bump, GitHub release) is generated by [semantic-release](https://semantic-release.gitbook.io/), run as a `release` job in `.github/workflows/ci.yml` that only fires after the `ci` job passes on a direct push to `main` (never on PRs). It analyzes commits since the last tag using the existing commit types, then creates a git tag + GitHub release (with auto-generated notes) via `@semantic-release/github`. No `CHANGELOG.md` file and no commit-back step — the GitHub Releases page is the changelog, and the release job never pushes a commit, only a tag. `@semantic-release/npm` is intentionally **not** used either — no `package.json` version is bumped; the git tag is the only source of truth.

**Build-time version stamping** is decoupled from semantic-release entirely. Any build computes its version with `git describe --tags --always --dirty` at the point the build is invoked:

- `config/deploy.yml` (Kamal configs are ERB-templated) runs `git describe` on the machine executing `kamal deploy` and passes the result as a Docker `--build-arg APP_VERSION=...`.
- `Dockerfile` threads `APP_VERSION` into both build stages: `-ldflags "-X main.version=..."` for the Go binary, `VITE_APP_VERSION` env var for the Vite build (Vite auto-exposes `VITE_`-prefixed vars as `import.meta.env.VITE_APP_VERSION`, no `vite.config.ts` change needed).
- The API exposes its version on `GET /api/v1/health`; the Vue dashboard shows it in the sidebar footer.

This means version reporting works identically whether the build came from a tagged release, an untagged commit on `main`, or a local dirty working tree (`dev` if no tags exist at all, `<tag>-<n>-g<sha>[-dirty]` otherwise) — it never depends on semantic-release having run.

## Consequences

- `kamal deploy` must be run from a checkout with the latest tags fetched (`git pull` / `git fetch --tags`) for the stamped version to reflect the latest release; a stale local clone just reports an older tag, not a broken build.
- No `package.json` version bump anywhere in the repo — avoids a redundant, easily-stale version source alongside git tags.
- No CHANGELOG.md commit means no husky/commitlint interaction to manage in the release job — semantic-release only pushes a tag, not a commit.
- If per-package independent releases are ever needed (e.g. `apps/api` and `apps/web` deployed separately), this would need revisiting — the current single `.releaserc.json` at the repo root assumes one version for the whole monorepo, matching the single-image deploy model.
