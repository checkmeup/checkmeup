# Decision backlog

Open questions that need an answer before (or early in) the relevant implementation. When decided, create a numbered ADR and remove the entry here.

---

- **WhatsApp provider** ([EP-15](../stories/ep-15-whatsapp-alerts.md)): Meta Cloud API directly, or a BSP (Twilio, MessageBird)? Affects setup complexity, per-message cost, and who handles template approval. Message template content (down alert, recovery alert) also needs drafting and submitting to Meta for approval before US-1502/US-1503 can ship — that approval lead time should be factored into scheduling, not assumed instant.

- **Signal: go/no-go** ([EP-16](../stories/ep-16-signal-alerts.md)): Signal has no official bot/business API — the only path is self-hosting `signal-cli` and registering a phone number as a bot account, which Signal's anti-abuse systems could flag or ban, and which adds an always-on process this repo has otherwise avoided ([ADR-001](001-worker-model.md): no Redis/job queue/external broker). Decide whether this is worth building at all before any EP-16 story starts, ideally backed by actual user demand rather than channel completeness for its own sake.

- **Teams webhook mechanism** ([EP-18](../stories/ep-18-teams-alerts.md)): Microsoft has been retiring the legacy Office 365 Connector "Incoming Webhook" in favor of Power Automate workflow webhooks (Adaptive Card payload). Re-verify the current retirement status and recommended mechanism immediately before implementing US-1801 — this is the kind of platform detail that can shift between when this was written and when the epic is actually picked up.

- **Manual incident schema** ([EP-24](../stories/ep-24-incident-management.md)): new `status_page_incidents` table decoupled from monitors/monitor-type, or extend the existing `cron_incidents`/`uptime_incidents` tables? The new-table approach looks like the better fit (a manual incident can span multiple monitors of different types, unlike the automatic incidents which are 1:1 with a single monitor's check transitions) but needs a real ADR before US-2401 starts.

- **Cron ping model: start vs. completion ping** ([EP-34](../stories/ep-34-zombie-job-detection.md), [EP-35](../stories/ep-35-overlap-detection.md)): both zombie (stuck-run) detection and overlap detection need a start-of-run signal distinct from today's single completion ping (`GET /ping/{token}`, EP-02 US-0202). Needs a decision on the new endpoint's shape (e.g. `GET /ping/{token}/start`) and where "run in progress" state lives (new column on `cron_monitors` vs. a new table) — must stay purely additive so monitors that never call it keep today's single-ping behavior unchanged. Needed before EP-34 US-3401 starts.

- **Multi-region check infrastructure** ([EP-32](../stories/ep-32-multi-region-checking.md)): the current architecture is one Hetzner VPS with no external queue/broker ([ADR-001](001-worker-model.md)) and no managed scaling ([ADR-006](006-infrastructure-hetzner-kamal-traefik.md)). Multi-region checking needs compute in more than one geographic location. Decide between additional regional VPS instances reporting back to the single Postgres instance (keeps ADR-001's no-broker constraint, but adds servers to provision/patch/pay for) versus a check-execution-as-a-service provider — and which regions to start with. Needed before US-3201 can be implemented.

- **API key scope enforcement** ([EP-26](../stories/ep-26-public-api-keys.md) US-2603, [ADR-028](028-api-key-auth-scope.md)): the `api_keys` table has no `scope` column and `RequireAPIKey` does no read-only/read-write check — harmless today since every `/api/v1/public` route is a `GET`, but a security review flagged that ADR-028's text reads as if this enforcement already exists. Add the `scope` column + `403`-on-non-`GET`-for-read-only-keys check *before* the first write endpoint ships under `/api/v1/public`, not after.

- **DDoS / WAF in front of the single Hetzner VPS**: today there's nothing between the internet and `kamal-proxy` beyond this repo's own per-route `httprate` limits ([ADR-013](013-rate-limiting.md)) — those bound abuse of a single account/IP, not a volumetric attack against the one box the whole app (API + DB + worker) runs on ([ADR-006](006-infrastructure-hetzner-kamal-traefik.md)). Decide whether to put a CDN/WAF (e.g. Cloudflare) in front, and if so, how it interacts with real client IPs already relied on for per-IP rate limiting and the public status pages' `Host`-based routing. Not urgent pre-launch-scale traffic, but worth deciding deliberately rather than by default. (Flagged during a security-skills session; explicitly out of scope for any automated skill — verifying it live would just be a self-inflicted DoS against production.)
