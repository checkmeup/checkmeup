# Webhook alerts

## Problem

Users want monitor events in their own automation (PagerDuty, custom scripts, chat tools Checkmeup doesn't integrate with) without waiting for a first-class integration for each.

## Users

Developers wiring Checkmeup into their own systems.

## Success signal

A user receives signed JSON events on their endpoint and can verify each one is from Checkmeup.

## Scope

- Webhook notification channels with an `https://` URL; several per org.
- A JSON `POST` per down and recovery event, signed with HMAC-SHA256 in `X-Checkmeup-Signature`.
- For a monitor in a project, the event also carries `projectId` and `projectName` (PRD projects); without one, the event has neither field.
- A signing secret generated by Checkmeup, visible and regeneratable in Settings.
- A test send, and the last delivery result in Settings.

## Non-goals

- Retries; one attempt per event.
- Custom payload templates.

## Acceptance criteria

- A webhook URL must start with `https://`.
  → test: apps/api/internal/handler/notification_channels_test.go "TestCreateNotificationChannel/webhook url must be https"
  → test: apps/web/src/lib/notificationChannelTypes.test.ts "requires webhook URLs to start with https://"
- After creation the API returns the URL masked (scheme, host and its last 4 characters); saving an edit with the URL left empty keeps the stored one (ADR alerting).
  → test: apps/api/internal/handler/notification_channels_test.go "TestMaskChannelURL"
  → test: apps/api/internal/handler/notification_channels_test.go "TestUpdateNotificationChannel/an empty or masked URL keeps the stored one (ADR alerting)"
  → test: apps/web/src/components/NotificationChannelsCard.test.ts "saves an edited webhook with an empty URL so the stored one is kept"
- Creating a webhook channel generates its signing secret on the server; a client-sent secret is ignored, also on update.
  → test: apps/api/internal/handler/notification_channels_test.go "TestCreateNotificationChannel/creates a webhook channel with a server-generated signing secret"
  → test: apps/api/internal/handler/notification_channels_test.go "TestUpdateNotificationChannel/updating a webhook's URL keeps the original signing secret, ignoring any client-supplied value"
- Every event is a JSON `POST` whose `X-Checkmeup-Signature` is the HMAC-SHA256 of the raw body under the channel's secret.
  → test: apps/api/internal/webhook/webhook_test.go "TestSend_PostsSignedJSONBody"
  → test: apps/api/internal/webhook/webhook_test.go "TestSign"
- A recovery event carries the downtime.
  → test: apps/api/internal/worker/worker_test.go "TestCheckUptimeMonitors/delivers a recovery webhook event with a non-zero downtime duration"
- Regenerating the secret signs future events with the new one.
  → test: apps/api/internal/handler/notification_channels_test.go "TestRegenerateWebhookSecret"
  → test: apps/web/src/components/NotificationChannelsCard.test.ts "regenerates the webhook signing secret"
- "Send test webhook" posts a signed sample and reports an unreachable endpoint as a failure.
  → test: apps/api/internal/handler/notification_channels_test.go "TestTestNotificationChannel/webhook posts a signed sample payload to a reachable endpoint"
  → test: apps/api/internal/handler/notification_channels_test.go "TestTestNotificationChannel/webhook with an unreachable endpoint surfaces as a 502"
- A delivery's success or failure (a non-2xx status, a timeout) is recorded on the channel and shown in Settings; failures aren't retried.
  → test: apps/api/internal/worker/worker_test.go "TestDispatchAlert/webhook channel delivers and records success on the channel row"
  → test: apps/api/internal/worker/worker_test.go "TestDispatchAlert/webhook channel records failure on a non-2xx response"
- A webhook pointing at a private or loopback address is refused.
  → test: apps/api/internal/webhook/webhook_test.go "TestSend_BlocksRestrictedAddresses"
- A slow endpoint is cut off after 10 seconds and never delays the check loop.
- Settings shows a snippet for verifying the signature.
